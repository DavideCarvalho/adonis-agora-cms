# i18n

Localization is storage-level, not a translation layer: a localized scalar gets one column per
locale (`title_pt_br`, `title_en`), and a localized child table gets a `_locale` column, so
array order is independent per language.

```ts
localization: {
  locales: ['pt-BR', 'en'],
  defaultLocale: 'pt-BR',
  fallback: true,             // empty value falls back to the default locale
  localizedRequired: 'default', // 'all' makes `required` apply to every locale
}
```

## Reading

```ts
await posts.findByID(id); // { title: { 'pt-BR': 'Oi', en: 'Hi' } }
await posts.findByID(id, { locale: 'en' }); // { title: 'Hi' }
```

With `fallback: true`, an empty `en` value returns the `pt-BR` value; with `fallback: false` it
returns `null`. Localized arrays behave the same way: a locale returns that locale's rows, no
locale returns `{ locale: rows[] }`, and an empty locale falls back to the default locale's
rows.

## Writing

```ts
await posts.create({ title: { 'pt-BR': 'Oi', en: 'Hi' } });
await posts.create({ title: 'Same' }); // every locale gets the value
await posts.update(id, { title: { en: 'Hello' } }); // pt-BR is preserved (deep merge)
```

`PATCH` merges plain objects recursively, so a partial locale map never wipes the other
languages. Arrays and scalars replace.

## Required

- `localizedRequired: 'default'` (default) — `required` applies to the default locale only, so
  translating can happen progressively.
- `localizedRequired: 'all'` — every locale is required.

## Unique

`unique: true` on a localized field is unique **per locale** (the unique index is on each
locale column), which matches what editors expect: the same slug can exist in both languages.
