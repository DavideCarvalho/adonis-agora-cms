---
title: Access control
description: Who can read and write each collection, document and field, with plain functions or @adonis-agora/authz.
icon: ShieldCheck
---

Set who can do what on each collection. A rule gets the request's `user`, and may be async.

```ts
import { collection, fields, requiresRole, requiresUser } from '@adonis-agora/cms';

collection('posts', {
  access: {
    read: () => true,
    create: requiresUser,
    update: requiresUser,
    delete: requiresRole('admin'),
  },
  fields: [fields.text('title')],
});
```

A rule that throws fails the operation, so a bug cannot open anything.

`requiresRole` matches `user.role`, a `user.roles` array, or authkit's `user.globalRoles`. With
`auth.authkit()` and the `authkitIdentityProvider()` user, `requiresRole('ADMIN')` checks the global roles
from the token, whether authkit runs in your app or on its own server. With a Lucid user, set
`lucidMirror({ injectGlobalRoles: true })` so the user carries them.

## Without a rule

| Environment       | Read | Anonymous write                                                     |
| ----------------- | ---- | ------------------------------------------------------------------- |
| Development, test | Open | Open, so a new app works before it has a login                      |
| Production        | Open | 401, unless the collection has a rule or `rest.publicWrites` is set |

Each operation is checked on its own: a rule for `read` says nothing about `create`. Reads stay public until
you set `read`. A signed-in user with no rule can do everything, so declare the rules when roles matter.

## Per document

For `read`, `update` and `delete` by id, the stored document arrives as `doc`:

```ts
access: {
  read: ({ user, doc }) => (doc ? doc.visibility !== 'private' || Boolean(user) : true),
}
```

`doc` is empty on a list, so return `true` there or use a constraint.

`doc` is always the whole stored document, fields hidden from the caller by `access.read` included, so a
rule can decide on an `owner` field nobody but admins may see. The caller only gets their trimmed view
afterwards. The same `doc` reaches `update` and `delete`, and the `update` rule also decides discarding a
draft, locking, scheduling and restoring a soft-deleted document. Reading a document's version history or
its schedule takes its `read` rule.

## Only some documents

Return a constraint instead of a boolean, and it becomes part of the query:

```ts
access: {
  read: ({ user }) =>
    user ? true : { field: 'visibility', operator: 'equals', value: 'public' },
}
```

Combine them with `{ and: [...] }` and `{ or: [...] }`.

## Per field

```ts
fields.select('role', {
  options: [{ label: 'Admin', value: 'admin' }],
  access: { update: requiresRole('admin') },
});
```

A field the caller cannot read is left out of every read, version snapshots included, and it cannot be
used in a `where` or a `sort`: that answers a 400 naming the field, since filtering on it would reveal its
value.

## Related documents

A populated relation follows the related collection's own rules, not the parent's. A related document the
caller cannot read (its `read` rule, a `where` it returns, a draft outside a draft read, a soft-deleted or
other-tenant document) stays a bare id, exactly like one that was deleted, and its hidden fields are left
out. The same applies to the relations stored in a version snapshot. `{ overrideAccess: true }` skips the
related rules too.

An `upload` whose `relationTo` is a collection of this CMS follows that collection's rules the same way:
one the caller cannot read is never handed to the media adapter and comes back as `{ id }`, the shape of a
missing file. An external media library receives the reader as `resolveMany(ids, { user, tenant })`, so it
can apply its own ownership rules.

## With a library

```ts
import { access } from '@adonis-agora/cms';

collection('posts', { access: access.authz('posts'), fields: [] }); // @adonis-agora/authz
collection('posts', { access: { update: access.bouncer(editPost) }, fields: [] }); // @adonisjs/bouncer
```

`access.authz('posts')` checks `posts.read`, `posts.create`, `posts.update` and `posts.delete`, and refuses a
guest. On a field, pass the check too: `access.authz('posts', (user, ability) => authz.can(user, ability))`.

## Your own code

The Local API applies the same rules with the instance's user. `cms.as(user)` scopes it to someone, and
`{ overrideAccess: true }` skips the rules for a job or a seed. It never crosses tenants.
